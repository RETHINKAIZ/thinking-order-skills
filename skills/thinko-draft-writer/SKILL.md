# 成稿写作中枢

> Thinking Order 合并版 skill：把零散信息整理成可直接发送、汇报或发布的成稿。

## 大原则

默认直接产出“可用初稿”，不要先长时间引导用户逐题回答。

只有在缺少收件人/受众、写作目的、关键事实这类阻塞信息时，才最多问 2 个问题。信息不足但仍可推进时，用占位符或假设继续写。

## 适用任务

- 工作汇报、周报、月报、项目总结、复盘。
- 邮件、通知、说明、申请、方案、倡议、发言稿。
- 将用户素材整理成 STAR、PREP、FABE、问题-方案-收益等结构。
- 根据模板快速生成标准化文档。

## 快速判断

| 场景 | 默认结构 |
|---|---|
| 周报/月报 | 本期结论 → 完成事项 → 问题风险 → 下期计划 → 需支持 |
| 项目汇报 | 目标 → 当前进展 → 关键成果 → 风险影响 → 决策/支持请求 |
| 复盘总结 | 背景 → 结果 → 做对了什么 → 问题原因 → 改进动作 |
| 邮件/通知 | 目的 → 关键信息 → 影响 → 行动要求 → 截止时间 |
| 方案/建议 | 结论 → 理由 → 执行方案 → 资源需求 → 风险预案 |
| 演讲/发言 | 开场 → 观点 → 例子 → 行动号召 → 收束 |

## 工作流程

1. **识别文体和对象**：判断是向上汇报、平级沟通、客户说明还是公开表达。
2. **抽取事实**：从用户材料中提取目标、动作、结果、问题、时间、责任人。
3. **选择结构**：按场景套用最合适模板，不展示过多备选。
4. **直接成稿**：输出完整初稿；缺失信息用 `[待补充]` 标出。
5. **附优化建议**：只给 2-3 条最关键的补充建议。

## 输出模板

```markdown
## [标题]

[可直接使用的正文]

---

### 信息缺口
- [需要用户补充的关键事实]

### 可选优化
- [更正式/更简短/更有说服力的调整方向]
```

汇报类优先用表格压缩信息：

| 模块 | 内容 |
|---|---|
| 核心结论 |  |
| 已完成 |  |
| 风险问题 |  |
| 下步计划 |  |
| 需支持 |  |

## 质量标准

- 先给成稿，再给解释。
- 向上汇报要结论先行，避免流水账。
- 对外沟通要克制、明确、可执行。
- 负面问题要写影响和补救，不甩锅。
- 不编造数据；缺失指标用 `[待补充]`。

## 低 Token 规则

- 不逐个问题收集信息，除非没有这些信息就无法写。
- 不列一堆模板让用户选；直接选一个最合适的。
- 不输出长篇方法论；把方法体现在成稿结构里。
